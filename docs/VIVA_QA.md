## Section 1: Architecture & System Overview (Q1–Q8)

### Q1: What is the core problem that Skill-Swap solves, and what is its primary technical innovation?
**Answer:**
Traditional learning platforms impose monetary barriers by charging per course or per hour, while classical barter boards suffer from the *double coincidence of wants* (User A teaches what B wants, but B does not teach what A wants). Skill-Swap solves this through a **hybrid matching and skill-credit architecture**:
1. **Algorithmic Matching Engine:** Detects and prioritizes mutual two-way swaps with top scores (base 100).
2. **Sovereign Skill-Credit Currency:** Enables one-way swaps (base 50) using a time-banking credit model (1 hour taught = +1 credit, 1 hour learned = -1 credit), backed by an atomic dual-signoff protocol.

---

### Q2: Why did you choose a monorepo structure instead of separate polyrepo repositories?
**Answer:**
A monorepo structure (`/backend`, `/web`, `/mobile`, `/docs`) was chosen because:
- **Shared Domain Models:** Data contracts (such as User, Skill, Session, and Transaction schemas) must stay synchronized across the web frontend, mobile application, and backend REST APIs.
- **Unified CI/CD & Testing:** A single root command (`docker-compose up`) builds the entire distributed system with all services and dependencies.
- **Simplified Project Evaluation:** All documentation, test cases, and code are co-located in a single repository for academic evaluation.

---

### Q3: How do the Web and Mobile applications interact with the Backend?
**Answer:**
Both clients interact with the backend using the same unified REST API over HTTP/JSON and Socket.io over WebSockets:
- **Web App (React/Vite):** Uses Axios with a centralized request interceptor that injects `Authorization: Bearer <token>`, with reverse-proxying through NGINX in production.
- **Mobile App (Flutter):** Uses `http.Client` with dynamic host resolution (`10.0.2.2:5000` on Android emulator and `localhost:5000` on iOS/Web) and saves JWT tokens in `SharedPreferences`.

---

### Q4: What happens if MongoDB is not locally running when the application starts?
**Answer:**
In `src/config/db.js`, the connection layer implements an **automatic fallback to `mongodb-memory-server`** when `NODE_ENV` is `development` or `test`. If a connection to `mongodb://127.0.0.1:27017/skillswap` fails with `ECONNREFUSED`, the system automatically spins up an in-memory MongoDB instance on an available ephemeral port. This allows the backend, test suite, and seed scripts to run without manual database configuration.

---

### Q5: How does the platform prevent unauthorized users from accessing the Admin dashboard?
**Answer:**
Access is enforced at two independent layers:
1. **Backend Middleware (`authorizeRoles('admin')`):** Verifies the decoded JWT payload contains `role: 'admin'`. If not, it throws an `ApiError.forbidden('Forbidden: Access denied')` (HTTP 403).
2. **Frontend Route Guard (`RoleRoute`):** The React router wraps `/admin` in `<RoleRoute role="admin">`. Non-admin users are automatically redirected to `/dashboard`.

---

### Q6: What is the role of NGINX in your Docker Compose deployment?
**Answer:**
NGINX acts as a multi-stage production web server and reverse proxy:
1. **Serves Static SPA Assets:** Hosts the compiled production bundle (`dist/`) generated by Vite.
2. **Handles Client-Side Routing:** Uses `try_files $uri $uri/ /index.html;` so React Router can handle deep URLs without 404 errors.
3. **Reverse Proxies `/api/`:** Forwards API calls to `http://backend:5000/api/`.
4. **WebSocket Upgrades:** Forwards `/socket.io/` requests to the Node backend with `Upgrade` and `Connection "upgrade"` headers.

### Q7: What design patterns did you employ in the Backend architecture?
**Answer:**
- **Layered Architecture Pattern:** Clean separation of concerns across `routes`, `controllers`, `services`, `models`, and `middleware`.
- **Factory & Singleton Patterns:** The `ApiClient` and Socket instance maintain singletons across application lifecycles.
- **Adapter/Facade Pattern:** `walletService.js` wraps both MongoDB replica set transactions and standalone conditional `$inc` atomic updates behind a unified interface.
- **Observer/Pub-Sub Pattern:** Socket.io event emissions for real-time notifications and chat messages.

## Section 2: Database Design & Mongoose Schemas (Q9–Q16)

### Q9: Why did you choose MongoDB over a Relational Database (like PostgreSQL)?
**Answer:**
1. **Hierarchical Document Modeling:** User profiles store structured sub-documents such as availability (days and time slots) and multi-coordinate location arrays without requiring complex 3-way table joins.
2. **Flexible Skill Attributes:** Different skill categories (Coding, Languages, Music) can carry distinct proficiency levels, descriptions, and metadata.
3. **High Velocity Chat & Notifications:** Unread message histories and notification feeds map cleanly to document collections with indexing.

---

### Q10: How do you enforce data integrity and prevent duplicate records in MongoDB?
**Answer:**
Through Mongoose schema constraints and **compound unique indexes**:
- **User Email:** Unique index on `email` prevents duplicate registrations.
- **Skill Name:** Unique index on `name` prevents duplicate catalog entries.
- **User Skills:** Compound unique index on `{ user: 1, skill: 1, type: 1 }` prevents a user from adding the same skill to their TEACH or LEARN list more than once.
- **Reviews:** Compound unique index on `{ session: 1, reviewer: 1 }` prevents duplicate reviews for the same session.

---

### Q11: Explain the relationship between `User`, `Skill`, and `UserSkill`.
**Answer:**
`UserSkill` functions as a many-to-many junction document between `User` and `Skill`. It stores the reference to the user, the reference to the catalog skill, the portfolio classification (`TEACH` vs `LEARN`), the user's declared proficiency (`Beginner`, `Intermediate`, `Expert`), and a custom description.

---

### Q12: How do you handle password storage securely?
**Answer:**
Passwords are never stored in plain text. A pre-save Mongoose hook in `User.js` checks `if (!user.isModified('passwordHash')) return`. If modified or new, it hashes the password with `bcrypt.hash(password, 10)`. The `User` schema schema also uses a `toJSON` transform that strips `passwordHash` before any user document is serialized in HTTP responses.

---

### Q13: What indexes did you build to optimize query performance?
**Answer:**
- `User`: `{ email: 1 }` (unique), `{ "location.city": 1 }` (proximity lookups), `{ status: 1 }`.
- `Skill`: `{ name: 1 }` (unique), `{ category: 1 }`, `{ status: 1 }`.
- `UserSkill`: Compound index `{ user: 1, skill: 1, type: 1 }` (unique), `{ skill: 1, type: 1 }` (for teacher matching).
- `Message`: `{ conversationId: 1, createdAt: -1 }` (for message history retrieval).
- `Session`: `{ teacher: 1, status: 1 }`, `{ learner: 1, status: 1 }`, `{ scheduledAt: 1 }`.

---

### Q14: How does MongoDB handle transactions, and how did you address standalone MongoDB instances in testing?
**Answer:**
MongoDB supports multi-document ACID transactions using `mongoose.startSession()`. However, transactions require a replica set. In local standalone environments, `startSession().withTransaction()` fails with a replica set error. `walletService.js` catches this error and **falls back to conditional atomic operations**:
`User.findOneAndUpdate({ _id: learnerId, creditBalance: { $gte: credits } }, { $inc: { creditBalance: -credits } })`. This ensures atomic balance checks and updates on both replica sets and standalone instances.

---

### Q15: What is the purpose of the `CreditTransaction` collection?
**Answer:**
The `CreditTransaction` collection serves as an **immutable audit ledger**. Rather than merely mutating a single number on the user profile, every credit change creates a ledger entry with `user`, `session`, `amount`, `type` (`EARN`, `SPEND`, `BONUS`, `REFUND`), `balanceAfter`, and `createdAt`. This allows users to view their complete transaction history and enables reconciliation if a discrepancy arises.

---

### Q16: How do you calculate user ratings without performance degradation?
**Answer:**
Instead of calculating `sum(ratings) / count` on every profile visit, the user document maintains running fields: `ratingAverage` (float) and `ratingCount` (int). When a new review is submitted in `reviewController.js`, it calculates:
$$\text{newAverage} = \frac{(\text{oldAvg} \times \text{oldCount}) + \text{newRating}}{\text{oldCount} + 1}$$
$$\text{newCount} = \text{oldCount} + 1$$
This updates in $O(1)$ constant time.

## Section 3: Matching Algorithm & Credit Economy (Q17–Q24)

### Q17: Walk me through the mathematical scoring formula of the Matching Engine.
**Answer:**
The score is calculated on a scale of 0 to 100:
1. **Base Score:**
   - **Mutual Swap:** $+100$ points if User A teaches what Candidate B wants AND Candidate B teaches what User A wants.
   - **One-Way Swap:** $+50$ points if Candidate B teaches what User A wants, but User A does not teach what Candidate B wants.
   - **No Match:** $0$ points.
2. **Bonus Factors (up to 50 points total):**
   - **Location Bonus (+15):** User and Candidate reside in the same city.
   - **Availability Bonus (+15):** User and Candidate share overlapping days of the week.
   - **Rating Bonus (+10):** Candidate has an average rating $\ge 4.5$ ($+5$ if $\ge 4.0$).
   - **Proficiency Fit (+10):** Teacher proficiency is higher than Learner proficiency (e.g. Expert teaching a Beginner).
$$\text{Score} = \min(100, \text{Base} + \text{Bonuses})$$

---

### Q18: How does the system handle score ties when multiple candidates have the same score?
**Answer:**
In `matchingService.js`, candidates with identical scores are deterministically sorted using secondary and tertiary tie-breakers:
1. Candidate `ratingAverage` (descending)
2. Candidate `ratingCount` (descending)
3. Account creation date (earlier members first)

---

### Q19: What is the Dual-Confirmation Protocol, and why is it critical?
**Answer:**
In a skill exchange, disputes may arise if one party claims a session took place while the other claims a no-show. The Dual-Confirmation Protocol requires **both** participants to mark the session as "Completed" on their respective dashboards. Credits only transfer when:
$$\text{teacherConfirmed} = \text{true} \quad \land \quad \text{learnerConfirmed} = \text{true}$$
If only one party confirms, credits remain untouched in the learner's wallet until resolved.

---

### Q20: What happens if a session is cancelled? Does anyone lose credits?
**Answer:**
No. If a session is cancelled by either party prior to dual completion, its status changes to `cancelled`. `walletService.js` has a guard rule: cancelled sessions never trigger credit transfers. The learner retains their credits without penalties.

---

### Q21: What prevents a user with 0 credits from booking a session?
**Answer:**
During session proposal (`POST /api/sessions`), `sessionController.js` calculates the required credits based on duration (e.g., 60 minutes = 1 credit). It checks the learner's `creditBalance`. If `learner.creditBalance < requiredCredits`, it rejects the proposal with HTTP 400 Bad Request (*"Insufficient credits to book this session"*).

---

### Q22: Can a user send a swap request to themselves?
**Answer:**
No. In `requestController.js`, the first validation rule is:
`if (receiverId === req.user._id.toString()) throw ApiError.badRequest('You cannot send a swap request to yourself')`.

---

### Q23: How do you prevent duplicate pending requests between the same users?
**Answer:**
Before creating a request, `requestController.js` queries:
`MatchRequest.findOne({ sender: req.user._id, receiver: receiverId, status: 'pending' })`.
If found, it returns `409 Conflict` (*"A pending request already exists"*).

---

### Q24: What is the starting credit balance for a new user, and what is the economic rationale?
**Answer:**
New users start with **2 complimentary credits**. This addresses the cold-start problem: without initial credits, a new user who doesn't immediately find an exact mutual swap could never book their first learning session to experience the platform.

## Section 4: Real-Time Chat & Sockets (Q25–Q30)

### Q25: How does Socket.io authenticate incoming WebSocket connections?
**Answer:**
In `socketService.js`, the Socket.io server registers a connection middleware:
`io.use((socket, next) => { ... })`. It extracts the JWT token from `socket.handshake.auth.token` or headers, verifies the token using `jwt.verify(token, secret)`, attaches the decoded `user` object to `socket.user`, and joins a personal notification room named `user_${user._id}`.

---

### Q26: How do you prevent unauthorized users from chatting with each other?
**Answer:**
Both at the WebSocket emission level and the REST controller level (`messageController.js`), the system checks for an accepted match:
`MatchRequest.findOne({ $or: [{ sender: A, receiver: B }, { sender: B, receiver: A }], status: 'accepted' })`.
If no accepted swap request exists between the two users, messaging is rejected with `403 Forbidden`.

---

### Q27: How are typing indicators implemented without overwhelming the server?
**Answer:**
On the client (Web and Mobile), input changes emit a `typing:start` socket event to the recipient's room. A **1500ms debounce timer** resets on every keystroke. When typing pauses for 1.5 seconds, the client emits `typing:stop`.

---

### Q28: How do read receipts work in the chat module?
**Answer:**
When messages are created, `readAt` is initialized to `null`. When the recipient opens the conversation or receives an incoming message while the chat window is active, the client calls `PATCH /api/conversations/:partnerId/read`. This updates `readAt = new Date()`. The sender's UI updates the checkmark icon from single gray (sent) to double blue (read).

---

### Q29: What happens if a recipient is offline when a message is sent?
**Answer:**
The message is saved to MongoDB. The socket service checks if the recipient has an active socket connection. If offline, the message remains stored with `readAt: null`. When the recipient next logs in, `GET /api/conversations` shows an unread message badge count.

---

### Q30: What is the fallback mechanism if the WebSocket connection fails?
**Answer:**
In `web/src/pages/ChatPage.jsx` and `mobile/lib/screens/chat_screen.dart`, message dispatch checks `socket.connected`. If the socket is disconnected or fails, the client falls back to calling the REST endpoint `POST /api/conversations/:targetUserId/messages`.

## Section 6: Security, Testing & Defense (Q36–Q40)

### Q36: How does the system defend against NoSQL injection attacks?
**Answer:**
Attackers may attempt NoSQL injection by passing query objects containing `{"$gt": ""}` to bypass authentication or filter clauses. Two layers protect against this:
1. `express-mongo-sanitize`: Middleware that recursively strips `$` and `.` characters from incoming request bodies, queries, and headers.
2. Strict type-checking in controllers (e.g. `typeof search === 'string'`) before calling string operations.

---

### Q37: How does the platform defend against Cross-Site Scripting (XSS)?
**Answer:**
1. Custom `xssClean.js` middleware sanitizes HTML tags and `<script>` elements from all incoming string fields.
2. React's JSX engine escapes variables during rendering by default.
3. Helmet sets security headers including `Content-Security-Policy` and `X-XSS-Protection`.
